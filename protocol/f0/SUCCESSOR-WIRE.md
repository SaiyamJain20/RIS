## 1. Error vocabulary: reasons on existing codes (option E1, recommended) [prop]

v1 `Error` is closed: `{code, message}` with 21 codes (`hmbc.schema.json` `$defs/Error`). `CONFLICT` and `QUORUM_UNAVAILABLE` (named in SIGNING-RULES) are **internal reasons**, not new codes:

- **E1 (recommended):** the successor `Error` gains two optional members, `reason` (a closed enum) and, for collection failures only, `collection` (section 3). `code` stays one of the 21 v1 values; consumers that ignore `reason` keep working.
- **E2 (alternative):** new top-level codes. This widens the shared vocabulary that the ledger's `ErrorCode` enum also uses, and either leaves the two enums inconsistent or forces a ledger change. Not recommended.

Why `INSUFFICIENT_QUORUM` is **not** reused for "the collector never obtained three signatures": that code means *the ledger rejected a submitted certificate* (it is already listed in `collect_decision`'s errors and in `QuorumLib`). A collector timeout means *no certificate was ever submitted*. An oracle must tell FL-3 (two witnesses down, nothing submitted) from a ledger rejection (FL-4/FL-5/F-23), so the timeout is `ADAPTER_UNAVAILABLE` with reason `QUORUM_UNAVAILABLE` and the per-witness evidence. A missing quorum is therefore never `POLICY_DENIED` and never a success.

| `reason` | `code` | Meaning |
|---|---|---|
| `CONFLICT_PINNED` | `STALE_STATE` | the witness's record for the conflict key holds a different effect value that is not yet dead (SIGNING-RULES section 2) |
| `PROPOSAL_MISMATCH` | `STALE_STATE` | the proposal differs from the witness's own derivation; the message names the field |
| `QUORUM_UNAVAILABLE` | `ADAPTER_UNAVAILABLE` | the collection deadline passed with fewer than q distinct valid signers; carries `collection` |
| `WITNESS_FAULTED` | `ADAPTER_UNAVAILABLE` | the witness's tripwire is set (section 4) |
| `LEDGER_UNREACHABLE` | `ADAPTER_UNAVAILABLE` | RPC failure while reading the ledger (today's behaviour, now named) |
| `STORE_MISSING`, `STORE_CORRUPT` | `ADAPTER_UNAVAILABLE` | the store is missing next to its marker, or fails its integrity check |
| `PROFILE_MISMATCH` | `WRONG_PROFILE` | manifest profile/enum differs from the contracts' `profile()` |
| `UNSEALED`, `WIRING_MISMATCH`, `GENESIS_MISMATCH`, `CODE_MISMATCH`, `MUTATIONS_MISMATCH`, `BUILD_MISMATCH` | `WRONG_DESTINATION` | D50 identity/build/wiring checks (D50 section 3) |
| `LEGACY_STATE`, `BINDING_MISMATCH`, `OWNER_MISMATCH` | `WRONG_DESTINATION` | the store belongs to another deployment, role or key, or is an unbound E store with rows |
| `BUILD_PIN_INVALID` | `MALFORMED` | the trusted build pins (immutable ranges, runtime length) are themselves malformed |
| `WITNESS_SET_MISMATCH` | `STALE_STATE` | set, threshold or version differs from the manifest, or PSC/KSSC/Governance disagree |

A key that is not a member of the sets stays `UNKNOWN_AUTHORITY` (`witness.py:39`, no reason). Validation refusals that already have a v1 code (`EXPIRED`, `REPLAY`, `WRONG_EPOCH`, ...) are unchanged and need no reason.

**Precedence at open (first failing wins).** Steps 1-8 read the ledger only and **touch no store**; step 9 uses a read-only connection and the marker file:
1 `LEDGER_UNREACHABLE`; 2 `PROFILE_MISMATCH`; 3 `BUILD_PIN_INVALID`; 4 `UNSEALED`; 5 `WIRING_MISMATCH`; 6 `GENESIS_MISMATCH`; 7 `CODE_MISMATCH`, `MUTATIONS_MISMATCH`, `BUILD_MISMATCH`; 8 `WITNESS_SET_MISMATCH`, then `UNKNOWN_AUTHORITY` (witness stores only);
9 `STORE_MISSING`, `STORE_CORRUPT`, `LEGACY_STATE`, `BINDING_MISMATCH`, `OWNER_MISMATCH`, then `WITNESS_FAULTED`. The checks that need no store run first so that a refusal before step 9 cannot have modified one.

`collection` rules: `outcomes` has exactly one entry per witness index, in index order. `status` is one of `signed`, `refused`, `invalid`, `silent`, `dissent`, `duplicate-only` (no valid first reply). `replies` counts every reply received from that witness; duplicates never add to the count of signers. A `refused` entry carries `code` and, when one exists, `reason`. `submittedSigners` is empty on failure and has exactly `quorum` addresses on success. The collection deadline and the per-witness reply timeout are **start-contract parameters with no default proposed here**: finite budgets belong to agent 3's numeric plan (A3-0058). A deadline can only be shorter than the proposal's remaining validity; eventual delivery after expiry does not rescue the operation.

**Recorded-value reports and adoption (StateCheckpoint only; revision 5, A3-0061).** Two valid checkpoint values can exist for one sequence inside the assumptions: any PBC block mined between two proposals gives a different `sourceBlockNumber/Hash` with identical epochs. A collection that is restarted by deriving a **newer** head would be refused `CONFLICT_PINNED` by every witness that already signed the earlier value, until that digest expires (an availability cost, never a safety loss). Decisions, receipts and governance actions cannot pin themselves this way (a decision is a pure function of the request and the current checkpoint; a receipt of the `GrantIssued` block; a governance action is supplied whole by the caller), so the rules below apply to checkpoints only.
1. **Retain the proposal.** Within one collection the pool derives the proposal **once**, keeps its bytes, resends it verbatim on any retry to witnesses that have not returned `signed`, and never re-derives. A witness that already signed that exact digest returns its stored signature.
2. **Refusal carries the recorded value.** A witness refusing a checkpoint proposal with reason `CONFLICT_PINNED` returns, in the single-witness error, `recorded` = `{message, signature}`: the checkpoint it recorded for that sequence (the digest with the latest `expiresAt` it signed) and **the signature it already issued for it**. It is public data; no new signing happens and no key is used. `recorded` appears nowhere else.
3. **Valid report.** The pool treats a report as valid only if it came from that witness over its supervised channel, its `sequence` equals the proposal's, and the signature recovers, over the digest the pool computes itself from `message` under the deployment's HMBCState domain, to that witness's configured address. A report that fails makes that witness's outcome `invalid`.
4. **Inconsistent reporter (R4).** A witness whose valid reports in the snapshot contain **two or more different values** is **inconsistent**: it contributes **nothing** to adoption, and every value and signature it returned is kept as evidence in `inconsistentReports`. Repeating the **same** value is not inconsistency (the witness counts once). The policy is **order-independent**; a first-report projection would depend on arrival order. Honest witnesses record one value per key; one can return two only if another collector got it to sign in between, so the exclusion is conservative: it only removes adoption options, it never adds one. An equivocator cannot help adoption and cannot, by itself, block it (the other witnesses still count).
5. **Adoption rule.** Among the **consistent** witnesses, the pool adopts a value iff **exactly one value** has at least **two distinct** witnesses reporting it. With no such value, or with two or more (an ambiguous split), it adopts nothing and keeps collecting until the deadline.
6. **Decision snapshot and late reports (R5).** The **decision snapshot** closes at the first of: all four witnesses have replied (any reply), or the 5 s per-witness reply timeout has elapsed from the start of the fan-out. The adoption decision is taken **once**, on the snapshot's reports **only**. A report that arrives after the snapshot closed is a **late report**: it is kept as evidence in `lateReports` and it **neither cancels nor creates** an adoption. Waiting for all four replies is bounded by the reply timeout and may end in a timeout; it never extends a deadline. Consequence, stated plainly: the same four reports can adopt **different values in different arrival orders** (a prefix of A,A adopts A even if B,B arrives late; a prefix of B,B adopts B even if A,A arrives late). Each adopted value was recorded by an honest witness (f <= 1), so either is safe; which one lets the collection finish depends on which value the not-yet-pinned witnesses can still validate.
7. **Re-proposal.** After adopting, the pool re-proposes the adopted message **verbatim, with its recorded `expiresAt`**, to every witness that has not signed it, in a second round with its own 5 s per-witness timeout **inside the original collection deadline** min(10 s, remaining - 2 s): replies after that deadline are ignored and nothing is extended. Each witness validates it independently (SIGNING-RULES section 3 and the conflict rule of section 2, both unchanged): an expired value is refused `EXPIRED`, a stale one `STALE_STATE`, a value that conflicts with a live record `CONFLICT_PINNED`. Adoption happens at most once per collection and is skipped when the adopted message has 2 s or less of validity left.
8. **Evidence.** The snapshot is `collection.recordedReports` (consistent witnesses: `witnessIndex` strictly ascending, each witness at most once, `message`, `signature`) together with `collection.inconsistentReports` (`[{witnessIndex, reports:[{message, signature}, ...]}]`, ascending, each with at least two **distinct** messages in canonical order); the two lists are **disjoint** and are **exactly** the partition the reference `pool_adoption.classify` computes from the snapshot's reports (the checker recomputes it). `collection.lateReports` (`[{witnessIndex, message, signature}]`, sorted by witness index then canonical message) holds the late reports and is evidence only. `collection.adopted` = `{message, reporters}` is present **iff** the adoption rule yields a value on the **snapshot**, equals it, and `reporters` are the consistent witnesses reporting it (at least two). On success the certificate is over `adopted.message`.
**Why this is safe.** The pool is untrusted and keyless, the witness conflict rule is untouched, and no witness signs anything it did not validate itself: adoption only makes the pool converge on a value that honest witnesses already hold. A Byzantine witness may report anything, but adoption needs a second distinct reporter, so with at most one Byzantine witness an adopted value was recorded, and independently validated, by an honest witness (exhaustively checked in the abstraction). **Outside the bound** (two Byzantine witnesses agreeing on a fake value) the fake value is adopted (control A4); every honest witness still validates it itself, so the cost is availability, not safety. **Liveness is a design argument, untested:** the collection completes if three honest witnesses can validate the adopted value; if the honest witnesses split, nothing is adopted and the sequence stays pinned until the earlier digests die (at most the 60 s checkpoint maximum).

## 3. Evidence export for witness stores [prop]

Like `worker_log` for the worker: `python -m hmbc_protocol.witness_state --state-dir D --evidence` opens the store **read-only** and prints the conflict records, digests, `superseded` history with its death evidence, the last observation per chain, the fault log and the binding (`--binding` as in D50). It is not an adapter operation and not listed in `adapter.json`. Raw signatures are not secrets; no key material is ever printed.

## 4. Tripwire: FAULTED response and recovery [prop]

Entered when, for a chain a signing operation reads, `latest.number` or `latest.timestamp` is **lower** than the last stored observation, or the hash stored for the last observed number changed (SIGNING-RULES section 6).

- **Persisted first.** The witness writes `faulted = {reason, previous observation, new observation}` to its store before answering; a restart stays FAULTED. If that write fails it still refuses.
- **Response.** Every signing operation answers `ADAPTER_UNAVAILABLE` / `WITNESS_FAULTED` until cleared. Read-only evidence export keeps working.
- **Clear.** An explicit operator command, `python -m hmbc_protocol.witness_service --state-dir D --clear-fault --note TEXT`. It **never deletes or rewrites signing history**: conflict records, digests and `superseded` rows stay; it appends a row to an append-only `fault_log` (old fault, the observation it was cleared against, the note) and sets the new observation baseline to the chain's current `latest`.
- **Scope of the claim.** A run that contains a clear is **outside the safe-ledger assumption for the interval it covers**. Evidence must say so; a clear does not turn a regression or reorganisation into an in-scope safety result, and digests recorded before the fault keep their earlier expiries (they are dead only by the ordinary rule, observed on the new baseline).

## 5. Store state model, lifecycle and crash ordering [prop]

Two stores, two owners (D50 section 3): the worker store (`<state-dir>/worker/`, `owner = "worker"`, **no key and no membership check**) and each witness store (`<state-dir>/witness-<i>/`, `owner = "witness:0x<address>"`, membership in PSC, KSSC and Governance required).

**What is state (A3-0059 R2; revision 3 was wrong here).** In SQLite's WAL mode a **committed** transaction can live only in the `-wal` file until a checkpoint copies it into the main file. The committed state of a store is therefore the **main database file plus its `-wal` file** (and the `INITIALIZED` marker). The `-shm` file is a recreatable shared index and is **not** state. A checkpoint rewrites the main file and truncates the WAL **without changing the logical content**. Measured on SQLite 3.47.2 (`vectors/wal_state_experiment.py`, predictions written first, 8 of 8 hold; this reproduces agent 3's control independently): after a commit the main file's sha256 was unchanged and a 4152-byte WAL held the row; a read-only connection saw it; a copy of the main file alone did **not**; main plus `-wal` did; `immutable=1` ignored it; after the last close the WAL was gone, the main file bytes changed and the logical content was identical.
Consequences:
- **Oracle.** A refusal must be checked by a **logical snapshot**, not by main-file bytes: under the store's lock, one read transaction through a WAL-aware read-only connection (`mode=ro`, never `immutable=1`) hashes the schema and every row of every table in `rowid` order, plus the marker bytes. The same snapshot is taken before and after the refusal; they must be equal. Main-file bytes may change legitimately (a checkpoint) and are not the oracle. A write-on-refusal mutant that commits a row **only to the WAL** must be detected by this oracle, and a main-file-hash oracle must be shown to **miss** it (the oracle's own negative control).
- **A refused open performs no write transaction**: it uses a read-only connection and the marker file only, so it cannot create committed state. SQLite's `-shm` may appear and is not state.
- **Copy and restore (matrix F-27).** A consistent copy takes the main file **and** its `-wal` (and the marker) together while the owner process is stopped, or after `PRAGMA wal_checkpoint(TRUNCATE)`. Copying only the main file silently drops committed rows: that is itself a **rollback to an older state**, to be classified as F-27 (not locally detectable), not a harmless partial backup. The runner's copy/restore harness and the evidence export must preserve all committed WAL; never use `immutable=1` to read a store.
- **Crash guarantee, stated precisely.** With `synchronous=FULL` a commit has been written and fsynced when it returns, so a committed record **survives process death** (`SIGKILL`, `os._exit`), which is the only crash mode the tests inject. **Power loss and OS crash are not tested and no durability claim is made for them**; fsync settings alone are not a measured power-loss result, and they depend on the storage stack.

**Initialisation (fresh directory), in this order; signing is allowed only after step 5 (A3-0059 R3):**
1. create the state directory (mode 0700) and take `flock` on `.init.lock`. These are **permitted lock/directory metadata, not state**: a crash here leaves an empty directory and a lock file;
2. compute and verify the binding (section 1, steps 1-8) **before creating the database or the marker**;
3. create the database, schema and `meta` rows (`binding_v2`, `binding_v2_doc`, `owner`, `schema`) in one transaction; commit (`synchronous=FULL`);
4. write `INITIALIZED.tmp` containing `{binding_v2, owner, schema}`, fsync it, rename it to `INITIALIZED`, **fsync the directory**;
5. only now release the lock and allow signing.

**Crash points and what a restart does** (the injected mode is process death; the power-loss column is a design argument, **untested**):
| Crash after | State on disk | Restart |
|---|---|---|
| 1 or 2 | empty directory (and `.init.lock`), no database, no marker | initialise again |
| 3 | database with binding rows and **no** record rows, no marker | complete step 4 (nothing can have been signed: signing needs step 5) |
| 4, before the rename | as above plus `INITIALIZED.tmp` | delete the temp file, complete step 4 |
| the rename, before the directory fsync returned | **process death:** the rename is visible, marker present. **Power loss:** the rename may be lost, marker absent | process death: normal open. Power loss: as for crash 3 (no record rows exist because signing was not yet allowed), complete step 4 |
| the directory fsync returned | marker durable | normal open; signing may start |
| any, but record rows exist and the marker is missing | impossible by the ordering | `STORE_CORRUPT`, refuse |

**An existing store is never silently initialised.** If a database or a marker exists, the store is *opened*, not initialised. The only case that is *completed* rather than refused is the interrupted initialisation above: a database whose binding rows equal the computed `binding_v2` and `owner`, with **no** record rows and no marker. Everything else that is not a clean open refuses: a database without binding rows and with rows (`LEGACY_STATE`), a marker without a database (`STORE_MISSING`), a binding or owner that differs (`BINDING_MISMATCH`, `OWNER_MISMATCH`), a failed integrity check (`STORE_CORRUPT`).

**Open of an existing store:** steps 1-8, then read the marker file and open the database **read-only** (`mode=ro`, as `worker_log.py` does) to check `integrity_check`, `binding_v2`, `owner`, `schema` and the legacy rule; only after every check passes is a read-write connection opened. A refused open leaves the **logical snapshot** and the marker bytes unchanged (see the oracle above).
