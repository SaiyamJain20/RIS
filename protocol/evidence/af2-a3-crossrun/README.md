## Findings, worst first

### F1. A BindingExport can never be verified once the chain has moved since the store was initialised. Side: AGENT 3 (collector API), not the exporter. REAL, reproduced in three runs (runs 1 and 2 failed an assertion on it, run 3 records it as data; same numbers each time).
- `evaluation.binding_context_v2.verify_export` requires `export["anchor"] == {pbc: observations.pbc.anchor, dbc: observations.dbc.anchor}`. `evaluation.public_observations_v2.collect` reads ONLY `latest` (no parameter to select a block). The exporter prints the anchor the store was initialised at, which is what `protocol/f0/EXPORT-LAYOUTS.md` row `anchor` and D50-DEPLOYMENT-BINDING.md (sections 3 and 5) say it must be: "the pinned block at which the live fields were read, **so an observer can recompute at the same block**".
- Repro (stages S5/S6b, `results.json`, run 3): four live `witness_main` stores initialised with DBC head 9 and PBC head 18; one checkpoint accepted (the DBC moved to block 11, PBC unchanged); `collect` (latest) gives anchors pbc 18 / dbc 11; `verify_export_snapshot(..., kind="BindingExport")` -> `ValueError: Invalid deployment context: export anchor mismatch` for **all four** witnesses (`results.json` S6b has the exact text and both anchors per witness: export pbc 18 / dbc 9, observation pbc 18 / dbc 11; `allRefused: true`).
- Control (S6c): the same `collect`, same ABI files, same checks, but with a TRANSPORT SHIM that answers `eth_getBlockByNumber latest` with the export's own anchor block (my `Pinned` class in `scripts/crossrun.py.txt`; not agent 3 code) -> **ACCEPTED 4/4**. Worker side too (S10): `worker_log --binding` at its own anchor -> ACCEPTED. So everything else joins; only the anchor selection is missing.
- Why it bites in F: the anchor in my stores is written once at initialisation and kept for the life of the directory (also across a process restart). Any F run that has blocks produced after start-up (the heartbeat of F-29, accepted checkpoints) hits this. `WitnessEvidence` is NOT affected (it carries no anchor; S6a ACCEPTED 4/4 at latest).
- Suggested fix (agent 3's call): `collect(..., anchors={"pbc": {number, hash}, "dbc": {...}})` that reads code/views at those numbers and checks the hashes, or a documented rule that the runner pins `collect` to the export's anchor. I do not change the exporter: the anchor semantics are the accepted F0 text.

### F2. The WORKER store is not a cooperative writer, and its directory has no `.lock`. Side: BOTH (agent 3's documented contract vs the E worker code). REAL, measured (S10, S11).
- Agent 3's `locked_store` says "A cooperative writer must honor the same flock" and refuses a missing lock file. The worker directory (`<adapter state>/worker/`) holds `worker.sqlite`, `INITIALIZED` and `.init.lock` only. `locked_store(worker.sqlite, INITIALIZED, .lock)` -> `ValueError: Store lock/file unavailable: [Errno 2] No such file or directory`; with `.init.lock` it works and `verify_export_snapshot(BindingExport, expected_owner="worker")` is ACCEPTED (S10).
- But nothing in the worker honours that lock after construction: with `locked_store` holding `.init.lock` exclusively, an already constructed `Worker` committed a record write in 0.00 s (S11, run 3). Agent 3's `require_unchanged(before, after)` DID detect it (`Store logical state changed`): the failure is loud, not silent. A `Worker()` being constructed blocks until release with no timeout (2.64 s of a 3 s hold) and no refusal.
- Consequence: a worker snapshot is serialised only if the runner has no adapter operation in flight. A3's logical snapshot covers EVERY table, while `--binding` exports only the immutable binding rows, so any worker write changes the logical hash.
- Options: (a) runner choreography (snapshot the worker only when idle; nothing for me); (b) I add a `.lock` and hold LOCK_SH around worker write transactions. That edits `worker.py`, an E-listed path (it would be the 4th changed E-listed path; needs agent 3's explicit agreement and new E pins). I did NOT do it.

### F3. A live witness WAITS, it does not refuse, while agent 3 holds the exclusive snapshot lock. Side: choreography (document it). REAL (S9).
- Witness 3 was asked to sign while `locked_store` was held for 4.0 s: the reply (a valid signature) came back 4.01 s later, after the release. The store's `flock` wait is unbounded. A snapshot taken during an F scenario's signing window therefore turns a healthy witness into a "silent" one for the pool's deadline. The runner must not hold the lock across a signing window, and F oracles must not count that witness as faulty.
