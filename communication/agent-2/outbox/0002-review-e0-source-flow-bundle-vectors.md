## 1. Source flow as read (paper-supported unless marked)
Fig 6: (1) user -> PSC [certAX, data_id]; (2)-(3) PSC <-> TMSC verify credentials; (4) PSC -> ACSC [GID, verified attributes, data_id];
(5) ACSC -> KSSC [GID, data_id] after policy enforcement; (6)-(7) KSSC reads the encrypted record C from the data layer;
(8) KSSC partial-decrypts: C1 = Decr(C, GP, K_{GID,onDuty(X)}); (9) ACSC -> PSC [{C,C1}, trans_hash]; (10) PSC -> user [{C,C1}]
(III-D3: PSC sends the response to the user encrypted with the user's public key and to LSC). The user finishes with the
long-term key K_{GID,Doctor(X)} (Fig 5). The KSSC never holds long-term keys, so the paper says it need not be trusted for full
decryption (III-E2).
- GID possession (III-D2): RSC takes certAX plus proof of knowledge of skAX, assigns GID and returns it encrypted to pkAX; GID is then
  put in certificates of other authorities after the user proves possession. ABE keys are requested by the user out of band.
- Authority/attribute ownership: each authority owns its long-term roles (certs/CRL) and its temporal list TempACL_X; the temporal
  ABE key K_{GID,onDuty(X)} is generated by X's ABE authority and lives only in the KSSC's isolated store.
SOURCE AMBIGUITIES (agent-2 view; each needs an explicit CHOICE):
 S-a. Fig 6 step 5 passes only [GID, data_id] to the KSSC, but it must choose WHICH temporal key(s) to apply. CHOICE: the worker derives the
      temporal attribute set from the committed grant plus the record's policy descriptor, never from relay-supplied attributes.
 S-b. GID is "assigned by RSC" (III-D2) but our interface makes gid the user's signing address (D20). CHOICE accepted; consequence: no
      RSC-assigned secret GID is returned, so the "send GID encrypted to pkAX" step has no counterpart and is not modelled.
 S-c. The optional 'System' attribute (III-E2 Remark) is what forces EVERY access through the KSSC. Without it, a policy branch made only of
      long-term attributes (e.g. isDoctorAtHospital AND isTreating) is decryptable by a key holder out of band, bypassing PBC/DBC entirely.
      CHOICE for E (symbolic): model decryptability as a boolean over (long-term attrs held by user) AND (temporal/System attrs applied by
      worker); report separately whether a record's policy contains a worker-held leaf. A policy with no worker-held leaf is "not system-gated"
      and no E claim covers it.
 S-d. ABE key issuance (out-of-band, per authority) and the authority's check of GID possession are not specified. E does not model them;
      user long-term keys are fixture handles (section 3).
 S-e. Fig 6 shows the response as an unencrypted data-flow label; III-D3/E1 say it is encrypted to the user's key. recipientKeyHash binds
      that key; the paper-profile DBC tuple has no recipient field (ledger KSSC.sol line 42 notes this), so recipient binding exists only in repaired-e.
 S-f. Isolation assumptions the paper relies on (IV-A, V): containers/Kubernetes isolate nodes and the KSSC key store. These are assumed, not
      verified; an in-process worker here models the assumption and a compromised worker is a labelled stress case, not a paper counterexample.

## 2. Credential bundle (agent-2 proposal; adopts A1-0003 section 3 unchanged)
JSON wire form for CredentialBundle (decimal strings, lowercase hex, unknown fields rejected):
 { "certificates": [ { "cert": {issuer,gid,roles:[bytes32...],serial,validFrom,validUntil}, "signature": "0x<65B>" } ... ],
   "temporalClaims": [ {authority, role} ... ] }
Order: certificates strictly ascending by issuer; roles strictly ascending; temporalClaims strictly ascending by (authority, role).
The client REFUSES to emit an unsorted bundle (it never "fixes" order silently, because order is part of the digest). Where it lives: the user's
wallet fixture holds certificates; the user's request signature covers the request, not the bundle, so the bundle is bound only through
credentialDigest in the witness decision (A1-0003). Witnesses do not trust a relay-supplied record list: they re-run TMSC.checkCredentials(gid,bundle,atTime)
at the accepted PBC block and compare credentialDigest (matches interfaces v0 "do not accept relay-asserted attributes").
Reproduced: credentialDigest vector and 4 mutations (see section 4).

(`keccak256("hmbc-e0-synthetic-key:" || label)`); they are TEST-ONLY, appear in committed vectors, and must never be reused. The runner's JSON-lines
requests/responses and logs never contain private keys, temporal keys or plaintext keys. No JANUS Vault/API is used.
