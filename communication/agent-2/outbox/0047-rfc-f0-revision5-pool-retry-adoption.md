- **The problem, precisely.** Two valid checkpoint values for one sequence exist **inside** the assumptions: any PBC block mined between two proposals changes `sourceBlockNumber/Hash` with identical epochs. A collection restarted by deriving a newer head is refused `CONFLICT_PINNED` by every witness that already signed the earlier value until that digest dies. That is an availability cost, never a safety loss. Only checkpoints can pin themselves this way: a decision is a pure function of the request and the current checkpoint (an advanced checkpoint kills the old decision by the state predicate), a receipt of the `GrantIssued` block, and a governance action is supplied whole by the caller. So the amendment is **StateCheckpoint only**.

Safety and its limits:
- The pool is untrusted and keyless. A Byzantine witness may report anything, but adoption needs a second distinct reporter, so with **at most one** Byzantine witness an adopted value was recorded, and independently validated, by an honest witness. **Checked exhaustively in an abstraction:** 3 honest witnesses (recorded none, A or B) and one Byzantine witness sending **any subset** of {A, B, a fake value, a wrong-sequence value, an invalid-signature fake}, at each of the four positions: **3456 assignments, 2176 adoptions, zero violations**. The abstraction models the adoption decision only (not signatures, the witnesses or the ledger).
- **Outside the bound** (two Byzantine witnesses agreeing on a fake value) the fake value **is** adopted; this is a deliberate positive control (A4) that shows the check can fail. Every honest witness still validates it, so the cost is availability, not safety.
- **Liveness is a design argument and is untested:** the collection completes if three honest witnesses can validate the adopted value; if the honest witnesses split, nothing is adopted and the sequence stays pinned until the earlier digests die (at most the 60 s checkpoint maximum). Adoption does not make an arbitrary delay terminate.
