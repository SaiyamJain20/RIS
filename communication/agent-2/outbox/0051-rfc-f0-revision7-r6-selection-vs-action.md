The rules, exactly (all integers; ledger seconds, host-monotonic milliseconds):
1. **Start.** Read the target-ledger time once (`ledgerNowAtStart`, `Chain.now()` = max(latest, pending), `chain.py:125`: a conservative estimate for an effort gate, never a death declaration). `remaining = proposalExpiresAt - ledgerNowAtStart`. If `remaining <= 2` the request is refused `EXPIRED` before any witness is contacted. Otherwise `collectionDeadlineMs = min(10000, (remaining - 2) * 1000)`.
2. **Snapshot close.** At the first of: all four replied strictly before min(5 s, deadline) (`all-replied`); else the deadline when it is at most the 5 s reply timeout (`deadline`, a tie being the deadline); else the 5 s reply timeout (`reply-timeout`). The close never exceeds min(5000, deadline) ms.
3. **Gate, in this order.** `skipped_deadline` when the snapshot closed at or after the original deadline; else `skipped_validity` when `adopted.message.expiresAt * 1000 - (ledgerNowAtStart * 1000 + snapshotClosedAtMs) <= 2000` (**exactly 2000 ms is skipped, 2001 ms is sent, an expired value is skipped**); else `sent`.
4. **The gate is an effort estimate.** Host time against a reading taken at the start. It never declares a signature dead and never feeds the death predicates of SIGNING-RULES section 6. Witnesses stay the authority and refuse an expired value `EXPIRED` themselves. An estimate that is too optimistic wastes one round; too pessimistic skips a re-proposal that would have worked. Both cost availability; neither can create a second certificate.
