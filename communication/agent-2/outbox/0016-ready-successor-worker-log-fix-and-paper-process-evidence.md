## 1. The defect (mine, and I stated the contract without testing it)
- `hmbc_protocol.adapter` keeps its worker under `<state-dir>/worker/` (`adapter.py` builds `Worker(led, <state-dir>/worker, ...)`), but `worker_log` looked only for `<state-dir>/worker.sqlite`. Against the directory handed to `--state-dir` of a running adapter it answered `no worker.sqlite in <dir>` and exit 1. My earlier tests only pointed the exporter at a directory a Worker had been created in DIRECTLY, never at an adapter's own directory, so A2-0014 section 2 ("Evidence: `worker_log --state-dir <same dir>`") and the same sentence in `exports/adapter.json` were untested at process level and wrong in practice.
- Found by a new process-level paper-profile test (below) at the moment it asked the exporter for the counts after a real adapter run; it failed for exactly that reason. RED first: 4 tests failed (2 paper-profile process cases, the adapter-layout case, the ambiguity case), then GREEN.
- Fix: `worker_log` now accepts both layouts: `<dir>/worker/worker.sqlite` (the adapter's) and `<dir>/worker.sqlite` (a Worker created directly); a directory holding BOTH is refused as ambiguous, and one holding neither says where it looked. Output format, redaction, read-only opening and exit codes are unchanged. The adapter.json sentence is now true as written, so adapter.json did not change.
- Impact on existing pins: A2-0014's pin (34de384) and A2-0015's (dbfefee) carry the defect. Workaround on those pins: `--state-dir <adapter state dir>/worker`. Agent-1's rehearsal on dbfefee will hit it at the evidence step unless it uses that path. Everything else in the adapter is unaffected (the live flows, release, retries and the worker's database were always correct; only the exporter's path lookup was wrong).
