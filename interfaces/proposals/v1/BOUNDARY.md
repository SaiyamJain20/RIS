## Transport and operation association

UTF-8 JSON lines, one object per line, at most 1,048,576 bytes including any line terminator presented to the parser. Requests have exactly `schemaVersion`, `operation`, `input`, `deploymentManifest`; schemaVersion is `v1`. A request cannot select an executable, environment, mode or secret. The mode is fixed by the startup manifest and every successful E result says `adapterMode="symbolic"`. Duplicate keys, NaN/Infinity, non-finite parsed numbers, unknown/missing properties and noncanonical wire values reject. JSON transport whitespace is permitted; embedded final newlines in hex, uint and key handles reject.

`AdapterRequest` selects a closed input schema by operation. The full `LedgerDeployment` schema applies even though the current E0 signing adapter validates only the subset it consumes. No RPC call, signature recovery, ABI verification, dynamic epoch/expiry check or deployment identity equality is established by JSON Schema. Run `evaluation.schema.validate_json_line("AdapterRequest", line)` for parse plus structural/semantic validation. `validate_response(operation, value)` additionally selects the matching result: the generic `AdapterResponse` accepts any of the five declared E results and cannot by itself associate a result with a pending operation.

Responses have exactly `schemaVersion`, `ok`, `result`, `error`. Success requires a declared closed result and null error. Failure requires null result and `{code, message}`. Operation-specific responses allow known error classes, because malformed requests can fail before dispatch; the per-operation manifest narrows runtime behavior. Unknown operation/envelope/wire violations use MALFORMED, any manifest chain/PSC/KSSC binding mismatch uses WRONG_DESTINATION, unbuilt E operations use ADAPTER_UNAVAILABLE, and G rotation uses NOT_IMPLEMENTED_IN_PHASE (D27). Text is diagnostic and not a reason-class assertion.

UserKeyRef is exactly `keyref:user:[a-z0-9][a-z0-9-]{0,63}` by full-string matching. Only the user role is accepted in these two user inputs. A reference is resolved inside the adapter; it is neither a private key nor a public report field. E0's provider derives TEST-ONLY keys from labels and does not yet persist worker state; the schema does not claim otherwise.

## Proposed symbolic nested shapes (new choices requiring ACK)

`SymbolicRecord` is exactly `{dataId: Hash, owner: Address, payloadDigest: Hash}`. It contains a commitment to synthetic payload bytes, never plaintext or key material. `SymbolicPolicy` is exactly `{clauses: PolicyRequirement[][]}` with at least one nonempty clause. Each requirement is `{role: Hash, kind: "1"|"2", issuerMode: "0"|"1"|"2"}`, using Agent 1's ACSC tuple order and issuer enum: ANY=0, DATA_OWNER=1, SAME_AS_FIRST=2. OR combines clauses and AND combines requirements. Clause order is preserved; SAME_AS_FIRST in the first position is rejected to avoid an unanchored interpretation. The primary fixture is Doctor/kind1/ANY followed by OnDuty/kind2/SAME_AS_FIRST. Emergency context remains an explicit synthetic assumption, not a policy leaf or treating-relation claim.

Proposed commitments for Agent 2 review (not implemented by Agent 3): `policyDigest = keccak256(abi.encode(Requirement[][]))`, with each tuple `(bytes32 role,uint8 kind,uint8 issuerMode)`; `ciphertextDigest = keccak256(abi.encode(keccak256(bytes("HMBCSymbolicRecord/v1")), dataId, owner, payloadDigest, policyDigest, uint64(0)))`. UTF-8 payload bytes are committed by Keccak-256 before the adapter boundary. These are deterministic symbolic record identifiers, not ciphertext or an ABE security construction. E1 must reject a record/policy that disagrees with the actual registered ACSC record, owner and policy; input alone cannot grant access. G0 replaces the symbolic record/envelope definition through a new reviewed interface, with actual scheme/AAD vectors.

`SymbolicEnvelope` is exactly `{kind: "symbolic-partial/v1", token: Hash}`. Proposed token meaning: a TEST-ONLY random opaque 32-byte handle created by the worker after validating a committed, unexpired grant, persisted with the response/cache before any send. Its durable record binds every outer release field and the record policy. It contains no temporal/master/user secret and offers no cryptographic confidentiality. A retry resolves the same cached response only before the original grant expires. Completion requires the worker's stored binding and a matching user recipient key reference; a caller-supplied token or `decryptable` boolean is not authority. Implementing that behavior and crash/retry tests belongs to B-E1/B-E2. Deterministic tokens in the boundary vectors are constructed examples, never issued capabilities.

The draft collect result follows Agent 2's field list exactly. Canonical record order and temporal serial=0 apply through nested results and envelopes. Signature recovery, credentialDigest recomputation, historical PBC state at the decision block plus its timestamp, membership, TTL and dynamic epoch checks remain runtime duties. A valid deny certificate may be represented by result=0; it never authorizes a release. No denial receipt is added.

## ScenarioResult and observations

All ten normative fields are mandatory: `scenarioId`, `classification`, `observedEvents`, `assertions`, `latencyMs`, `gasUsed`, `encodedBytes`, `limitations`, `evidencePaths`. Classifications use SPEC's six values. Assertions are `{name: nonempty string, passed: boolean}`; SUPPORTED/REPAIR_SUPPORTED require nonempty passing assertions and evidence paths. Other executed classifications also require evidence; BLOCKED may have no assertions/evidence. This is a shape constraint, not evidence adjudication: copying booleans cannot pass `evaluation.gate`.

`latencyMs` is a finite nonnegative number or null for unmeasured trials; `gasUsed` is a decimal Uint256 string or null; `encodedBytes` is a nonnegative measurement integer or null. Null values retain failed/unexecuted trials rather than inventing zero performance. Limitations must have at least one nonempty entry. Evidence paths are relative POSIX paths without traversal; resolving files and checking their hashes remains the run collector's responsibility.

Every observed event has `type`, `requestDigest`, `timestamp` (Uint64 seconds). DBC_AUTHORIZED additionally has grantId, gid, dataId, kssc, destinationChainId, recipientKeyHash, keyEpoch=0. RELEASE_INTENT/RELEASE_SENT/OUTCOME_RECORDED additionally have grantId, gid, dataId. REQUEST_LOGGED/PBC_DECIDED have only the base fields. Unknown fields/events reject. This preserves the current independent oracle fixture shape; the E1 collector must save native receipts/worker logs and normalized-event mapping as evidence paths. Timestamp/event order is an observed causal sequence, never ordering blocks from different chains by block height. Intent/send/outcome and authorization are distinct facts; outcome is not proof of recipient delivery.
