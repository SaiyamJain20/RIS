# Candidate v1 — NOT FROZEN

These schemas instantiate A1-0003 and A3-0002 for review. The live normative interface remains v0. No ACK is inferred from publication. Run `python interfaces/proposals/build_schemas.py` to regenerate `hmbc.schema.json`; use `evaluation.schema.validate(name, value)` to apply JSON Schema and semantic checks. The custom uint formats enforce the exact unsigned width; pattern-only JSON Schema consumers must implement equivalent range checks. Canonical signatures require r in 1..n-1, low s and v=27/28. Recovery/signature identity is checked separately.

JSON uses decimal-string integers and lowercase hex. Credential records sort by `(kind, issuer, role)`; certificates sort by issuer; temporal claims/entries by `(authority-or-gid, role)`; roles and revoked serials strictly increase. Intervals require validFrom < validUntil. Empty credential bundles and zero-GID temporal entries are MALFORMED. E keyEpoch=0 and witness set=1. Decision signatures must be sorted by recovered address; the schema cannot recover keys or check dynamic witness membership. TTL/current epoch/checkpoint/revocation rules require state validation, not merely schemas.

Each implemented signed type carries an `x-eip712Type` annotation with the exact encodeType string, including nested dependencies. Signing code must use that explicit type definition rather than infer signing order from JSON. Regression tests compare annotations and property order with the owner-authored producer vectors. TempAclEntry and CredentialRecord also carry their hashed struct types.

The existing GrantReceipt definition (dbcResult=1) is a **superseded proposal**, retained pending the affected-party ACK process. A1-0008 revision 2 removes dbcResult and adds gid, dataId and witnessSetVersion; agent 3 ACKs that exact RFC in A3-0005. Agent-2 capability/semantics ACK is still absent, so receipt fields are not changed and no receipt implementation or signing vector is claimed. Do not use this definition for implementation/freeze. Revision 2 attests a past authorized matching DBC grant, permits late reconciliation, excludes denial receipts, and cannot establish release/delivery/decryption.

The adapter response envelope validates exclusivity and known error classes. Operation-specific input/result/deployment schema is OPEN until agent-2 supplies its source-flow review and sample exports. An opaque result object is not claimed to have strict internal validation. Deployment manifests/ABIs currently remain agent-1's proposed exports, not frozen schema contracts. Unsupported nested fields in defined signed/bundle types reject.

Positive/mutated cryptographic vectors retain agent-1 producer provenance and TEST-ONLY keys. Agent-3 recomputes them using eth-account/eth-abi. A full v1 freeze needs both peers to ACK the exact signed types, ABI placement, clock/retry/profile rules, schema/vector hashes and source map.

The schema document has 33 definitions. Evaluation record numbers (exit codes, elapsed time, optional schedule seed) are measurement metadata; ABI/EIP-712 unsigned values remain decimal strings. Deployment chain/block/TTL/version/mutation unsigned values will also remain decimal strings, consistent with A1-0007 and the owner sample exports. Agent-2 ACK and operation/deployment schema review remain required. The positive-control Scenario schema is intentionally a provisional fixture schema; E01/E02/E03 fault/input schemas require the post-E1 reviewed scenario expansion. RunManifest currently describes preflight evidence. ScenarioResult and complete operation/deployment schemas remain OPEN; no successful provider result is generated to bypass those gaps.
