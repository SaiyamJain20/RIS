## Transport and operation association

UTF-8 JSON lines, one object per line, at most 1,048,576 bytes including any line terminator presented to the parser. Requests have exactly `schemaVersion`, `operation`, `input`, `deploymentManifest`; schemaVersion is `v1`. A request cannot select an executable, environment, mode or secret. The mode is fixed by the startup manifest and every successful E result says `adapterMode="symbolic"`. Duplicate keys, NaN/Infinity, non-finite parsed numbers, unknown/missing properties and noncanonical wire values reject. JSON transport whitespace is permitted; embedded final newlines in hex, uint and key handles reject.

`AdapterRequest` selects a closed input schema by operation. The full `LedgerDeployment` schema applies even though the current E0 signing adapter validates only the subset it consumes. No RPC call, signature recovery, ABI verification, dynamic epoch/expiry check or deployment identity equality is established by JSON Schema. Run `evaluation.schema.validate_json_line("AdapterRequest", line)` for parse plus structural/semantic validation. `validate_response(operation, value)` additionally selects the matching result: the generic `AdapterResponse` accepts any of the seven declared E results and cannot by itself associate a result with a pending operation.

Responses have exactly `schemaVersion`, `ok`, `result`, `error`. Success requires a declared closed result and null error. Failure requires null result and `{code, message}`. Operation-specific responses allow known error classes, because malformed requests can fail before dispatch; the per-operation manifest narrows runtime behavior. Unknown operation/envelope/wire violations use MALFORMED, any manifest chain/PSC/KSSC binding mismatch uses WRONG_DESTINATION, unbuilt E operations use ADAPTER_UNAVAILABLE, and G rotation uses NOT_IMPLEMENTED_IN_PHASE (D27). Text is diagnostic and not a reason-class assertion.

UserKeyRef is exactly `keyref:user:[a-z0-9][a-z0-9-]{0,63}` by full-string matching. Only the user role is accepted in these two user inputs. A reference is resolved inside the adapter; it is neither a private key nor a public report field. The retained E0 provider export (b9564f0) derives TEST-ONLY keys from labels and does not persist worker state; later candidate code is not an integration READY. The schema does not claim otherwise.

## Proposed symbolic nested shapes (new choices requiring ACK)

`SymbolicRecord` is exactly `{dataId: Hash, owner: Address, payloadDigest: Hash}`. It contains a commitment to synthetic payload bytes, never plaintext or key material. `SymbolicPolicy` is exactly `{clauses: PolicyRequirement[][]}` with at least one nonempty clause. Each requirement is `{role: Hash, kind: "1"|"2", issuerMode: "0"|"1"|"2"}`, using Agent 1's ACSC tuple order and issuer enum: ANY=0, DATA_OWNER=1, SAME_AS_FIRST=2. OR combines clauses and AND combines requirements. Clause order is preserved; SAME_AS_FIRST in the first position is rejected to avoid an unanchored interpretation. The primary fixture uses role ids keccak256("HMBC.role.Doctor")/keccak256("HMBC.role.OnDuty"), with Doctor/kind1/ANY followed by OnDuty/kind2/SAME_AS_FIRST. Its policyDigest is 0x4bd063e1a4c348bf656f983104839fec2594aaee710b4627e9e46368ba1abc3a (independent cast result A1-0013, eth-abi reproduction A2-0006/Agent3). The record example uses dataId keccak256("HMBC.data.P1.MHR")=0x53ff15331656b9b303d95970634a992ed32268c5d9723c90ddc94ceeb397061e and fixture owner H2; the owner-generated prepare_request example uses a separate arbitrary dataId and is not a complete flow. Emergency context remains an explicit synthetic assumption, not a policy leaf or treating-relation claim.

Proposed commitments for Agent 2 review (not implemented by Agent 3): `policyDigest = keccak256(abi.encode(Requirement[][]))`, with each tuple `(bytes32 role,uint8 kind,uint8 issuerMode)`; `ciphertextDigest = keccak256(abi.encode(keccak256(bytes("HMBCSymbolicRecord/v1")), dataId, owner, payloadDigest, policyDigest, uint64(0)))`. UTF-8 payload bytes are committed by Keccak-256 before the adapter boundary. These are deterministic symbolic record identifiers, not ciphertext or an ABE security construction. E1 must reject a record/policy that disagrees with the actual registered ACSC record, owner and policy; input alone cannot grant access. G0 replaces the symbolic record/envelope definition through a new reviewed interface, with actual scheme/AAD vectors.

`SymbolicEnvelope` is exactly `{kind: "symbolic-partial/v1", token: Hash}`. Proposed token meaning: a TEST-ONLY random opaque 32-byte handle created by the worker after validating a committed, unexpired grant, persisted with the response/cache before any send. Its durable record binds every outer release field and the record policy. It contains no temporal/master/user secret and offers no cryptographic confidentiality. A retry resolves the same cached response only before the original grant expires. Completion requires the worker's stored binding and a matching user recipient key reference; a caller-supplied token or `decryptable` boolean is not authority. Implementing that behavior and crash/retry tests belongs to B-E1/B-E2. Deterministic tokens in the boundary vectors are constructed examples, never issued capabilities.

The draft collect result follows Agent 2's field list exactly. Canonical record order and temporal serial=0 apply through nested results and envelopes. Signature recovery, credentialDigest recomputation, historical PBC state at the decision block plus its timestamp, membership, TTL and dynamic epoch checks remain runtime duties. A valid deny certificate may be represented by result=0; it never authorizes a release. No denial receipt is added.

## ScenarioResult and observations

All ten normative fields are mandatory: `scenarioId`, `classification`, `observedEvents`, `assertions`, `latencyMs`, `gasUsed`, `encodedBytes`, `limitations`, `evidencePaths`. Classifications use SPEC's six values. Assertions are `{name: nonempty string, passed: boolean}`; SUPPORTED/REPAIR_SUPPORTED require nonempty passing assertions and evidence paths. Other executed classifications also require evidence; BLOCKED may have no assertions/evidence. This is a shape constraint, not evidence adjudication: copying booleans cannot pass `evaluation.gate`.

`latencyMs` is a finite nonnegative number or null for unmeasured trials; `gasUsed` is a decimal Uint256 string or null; `encodedBytes` is a nonnegative measurement integer or null. Null values retain failed/unexecuted trials rather than inventing zero performance. Limitations must have at least one nonempty entry. Evidence paths are relative POSIX paths without traversal; resolving files and checking their hashes remains the run collector's responsibility.

Every observed event has `type`, `requestDigest`, `timestamp` (Uint64 seconds). DBC_AUTHORIZED additionally has grantId, gid, dataId, kssc, destinationChainId, recipientKeyHash, keyEpoch=0. RELEASE_INTENT/RELEASE_SENT/OUTCOME_RECORDED additionally have grantId, gid, dataId. REQUEST_LOGGED/PBC_DECIDED have only the base fields. Unknown fields/events reject. This preserves the current independent oracle fixture shape; the E1 collector must save native receipts/worker logs and normalized-event mapping as evidence paths. Timestamp/event order is an observed causal sequence, never ordering blocks from different chains by block height. Intent/send/outcome and authorization are distinct facts; outcome is not proof of recipient delivery.

## Revision5 witness operations and key custody (Option A proposal)

A2-0008 identifies a real six-operation gap; A1-0016 confirms its ledger scope. The runner owns transaction submission; the adapter supplies independently verified witness artifacts. This is a proposed boundary, not E1 readiness. The order in repaired-e is collect_checkpoint → runner KSSC.acceptState → collect_decision → runner ACSC.consumeDecision → release → attest_grant → runner PSC.reportAttestedOutcome. A valid denied decision produces ACSC.AccessLog(allowed=false, POLICY_DENIED), no grant, and no consumed nonce; no receipt exists for denial. The witness signs ALLOW only when both historical credential verification and ACSC.evaluate(dataId, records) pass (A1-0017). An ALLOW for insufficient policy is a separate deviating-witness control: consumeDecision reverts POLICY_DENIED and does not emit the denial AccessLog.

collect_checkpoint accepts exactly an optional witnessSetVersion="1"; {} is valid. It never accepts a relay-supplied sequence, timestamp or source block. The witness reads a PBC block it treats as final under the safe-ledger assumption, records its hash/number, sourceChainId/PSC and TMSC.authEpoch, and the common policyVersion (1 in E). It reads the DBC current sequence and signs sequence+1, keyEpoch=0 and witnessSetVersion=1, using HMBCState/1/DBC/KSSC. expiresAt is at most the observed DBC block timestamp+60, and must still be strictly after the DBC inclusion timestamp. Ledger acceptance also requires nondecreasing epochs/policyVersion/sourceBlockNumber. These dynamic conditions are runtime checks; the schema checks only the frozen wire types.

collect_decision uses the accepted current DBC checkpoint. It must remain unexpired and describe the PBC state the witness verifies (block hash, authEpoch, policyVersion) without predating the forwarded request. Credential records are recomputed at that PBC block with that block timestamp. The decision binds its current sequence and expires no later than the request, checkpoint, or observed DBC timestamp+30. Any checkpoint accepted between collection and consumption invalidates the old sequence; a revocation between request and checkpoint requires a newly signed request. Preserve the original pre-revocation certificate for the pre-/post-barrier controls. Re-collection is bounded by D24; a relay cannot choose the witness's state.

attest_grant accepts exactly {grantId: Hash}. The witness reads KSSC.getGrant at a DBC block it treats as final and signs only an allowed, matching grant. It copies the request/gid/data/destination/epoch/original positive expiry and observed DBC block fields into GrantReceipt (HMBCReceipt/1/PBC/PSC); a missing or denied grant returns NOT_COMMITTED. It cross-checks PSC's forwarded request. Late attestation/reconciliation of that past grant may occur after expiry; it never authorizes a new release or demonstrates delivery/decryption. There is no denial receipt or on-chain light-client proof.

Option A requires the runner to hold only TEST-ONLY relay and H1..H4-ca-admin fixture signing keys for caller-restricted policyEnf/reportOutcome/reportAttestedOutcome and issuer-scoped list updates. They use the existing keccak256("hmbc-e0-synthetic-key:" || label) derivation and remain outside public reports. Witness, user and worker keys/handles resolve inside Agent2's process/state directory. The runner never signs witness artifacts. Paper profiles do not use acceptState or attested receipts; they use the configured relay's policyEnf/reportOutcome paths. Runtime key custody and funding/ports are E1 obligations, not current services.

Recipient-key fixture convention (A1-0015/A2-0007, A35): recipientKeyHash = keccak256(UTF-8 bytes("HMBC.recipient-key." || label)), where the label belongs to keyref:user:<label>. alice=0x98d796e3229ebf5c50610744cf35aece58511751e387e8eef569a0117bb07e5d; bob=0x5fe346cd69926d7120dff3cc020f4d36ad8093b7c9bb95c6ecea9705a3f8c537. The ledger stores the GID-signed Registration value; it does not derive it. Completion checks that the resolved user reference matches the grant's registered recipient commitment. This is a symbolic fixture convention; G0 must review the meaning for real recipient public-key bytes separately. No signing-vector migration is needed.

## Revision5 native observations and prospective schedules

OUTCOME_RECORDED joins gid/dataId from PSC.getRequest(requestDigest), or its verified AccessForwarded event, at the recorded PBC state; never from relay-supplied values. Native PSC OutcomeRecorded/AttestedOutcomeRecorded contain requestDigest/grantId/outcomeDigest/logId (plus dbcBlockNumber for attested), not gid/dataId. Save the native receipt, emitting address, request lookup/block and join checks as evidence. An attested receipt also provides checked fields. REQUEST_LOGGED maps LSC.LogRecorded(kind=REQUEST, subject=requestDigest) using its LogEntry timestamp. PBC_DECIDED maps PSC.AccessForwarded/AccessDenied. DBC_AUTHORIZED maps KSSC.GrantIssued, using its emitting KSSC address and deployment chainId. Paper grants retain relay-supplied requestDigest and zero recipientKeyHash. A DBC denial AccessLog or reverted consumeDecision has no new ObservedEvent variant; report its native evidence and corresponding assertions/error instead.

The repaired-e Bob control explicitly requires expectedLedgerChecks=[DBC_POLICY_DENIAL_LOGGED, NONCE_UNCHANGED]. The collector independently checks the bound native AccessLog and before/after nonce, then supplies true boolean values to the independent oracle's private observation ledgerChecks map. The public ScenarioResult stores named assertions and evidence paths, not that private map. POLICY_DENIED is normalized from the denial AccessLog even when consumeDecision returns zero without reverting. A missing/false/nonboolean check fails the oracle. Unit traces establish sensitivity only; copied booleans do not satisfy the integration gate.

CRASH_RESTART is a closed step with {action, offsetSeconds, workerHook:"release", crashPoint:"after-intent"|"after-send"}. The executor reads the whole schedule and arms this point BEFORE the immediately preceding RELEASE, restarts at CRASH_RESTART, then performs the following RELEASE retry before original expiry. No arbitrary hook/code is accepted. after-intent means intent plus cached response durable, before any send; after-send means a recorded attempted send, before outcome acknowledgement. The six crash cases carry a closed expected.worker record: one RELEASE_INTENT per grant, one RELEASE_SENT after an intent crash/retry, two after a send crash/retry, sameCachedResponse=true, delivery="unknown", expiredRetryError="EXPIRED". A separate retry at original expiry must add no intent/send and return EXPIRED. ScenarioResult assertions must state intent count, send-attempt count, same cached token/ciphertextDigest, original-expiry rejection, and delivery uncertainty, with worker-log/cache evidence paths. RELEASE_SENT is an attempt, never recipient acknowledgement or exactly-once delivery.

The subject-substitution case substitutes request.gid and preserves the original certificate, so repaired-e expects WRONG_SUBJECT; rewriting its decision digest too is a BAD_SIGNATURE control. Paper post-barrier schedules omit ACCEPT_CHECKPOINT because it is not applicable (otherwise WRONG_PROFILE), preserving their prospective stale-state gap. Wrong-issuer is SUPPORTED baseline behavior preserved in repaired-e. The catalog now has48 NOT_RUN cases, including forged tuple, wrong destination and fresh-relay-reference replay counterparts to owner ledger controls. All schedules remain E0 expectations; real hooks, results, recovery, faults and classifications require E1/E2 execution. Exact revised producer/consumer ACKs remain necessary before freeze.
