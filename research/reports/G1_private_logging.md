**Key observation (seed gap (a) confirmed, sharpened).** In both papers the "majority consent to retrieve logs" is an *access-control check over plaintext data that every PBC node already holds*. A curious insurer node can read (requester GID / CN, patient id, hospital, data type, timestamp) directly from its own ledger copy. Combined with RSC's on-chain GID<->certificate link (certificate = real name + organisation + role) and TempACL (GID, onDuty, period), the PBC is a globally replicated table of *which named clinician read which patient's record at which hospital when*, visible to every insurer and device manufacturer. This metadata is itself health information (e.g., "oncologist at hospital X accessed patient P"). The Lewko-Waters GID additionally makes a user's key requests across authorities linkable by design.

**Du et al. 2024 framing (OPENED, local PDF, Comput. Electr. Eng. 119:109547).** Intro: "recording access transactions on the blockchain depends on precisely executing access policies. This leads to the disclosure of the visitor's identity and the content of the accessed data to the entire network, thereby increasing the potential for privacy breaches by the data requester." Their scheme does NOT solve it (they do sensitivity-level hierarchical CP-ABE); conclusion lists "integrating privacy-preserving techniques, such as zero-knowledge proofs" as future work. So Du et al. is a problem-statement citation, not a competitor.

## 1. Candidate contributions (anchored in HMBC2020 mechanisms)

**C1 - SEAL-LOG: two-tier sealed, threshold-openable, completeness-checkable global log.** Replace each plaintext LSC record with `e = (D, epoch, outcome, tau, C_glob, C_dom, pi)`: D = target domain (public, needed for routing), tau = H(user nonce) unlinkable tag, C_glob = ElGamal encryption of GID under the PBC opening key (t-of-n of ALL stakeholders = the existing majorityConsent quorum), C_dom = encryption of (GID, record id, rule used, time) under domain D's opening key (t_D-of-n_D of D's stakeholders), pi = NIZK that the ciphertexts are well-formed and consistent with the credential proof of C2. `retrieveLog` becomes *cryptographic*: approving stakeholders post decryption shares + Chaum-Pedersen proofs on-chain, so (a) opening without quorum is impossible even for a node that reads raw chain state, and (b) every opening is itself logged ("auditing the auditors"). Two opening scopes: domain-internal audits open C_dom only within D; cross-domain disputes open C_glob via the global quorum. **Completeness across chains:** the ACSC/KSSC side records the same tau in the DBC; each epoch the DBC anchors a Merkle root of its tau-set on the PBC; anyone checks set equality, so a DBC access without a PBC entry (or vice versa) is publicly detectable without revealing content. This keeps the original "forensics-by-design / global verifiability / detectable policy modification" claims (Sec. V-A5) while removing who-what-when from insurers/manufacturers. *Exclusion-zone note:* do NOT make KSSC partial decryption conditional on a log-inclusion token (that is "capability-token-bound partial decryption", zone 2); the opening key is an audit key, not a gatekeeper key, and DKG is only a standard building block, not a claimed contribution.

**C2 - UNLINK-REG: unlinkable registration and temporal roles on the PBC.** RSC stores Com(GID) + threshold-escrowed Enc(certID || GID) instead of the plaintext GID<->certificate link (Sec. III-D2); TempACL_X is published as a Merkle root of Com(GID, role, from, to) instead of plaintext (GID, onDuty, period) (Sec. III-C); CRL_X as a sorted Merkle tree for non-membership. The PSC/TMSC (`getUserValidation`) verifies a ZK proof: "my committed GID is bound to a non-revoked certificate from a CA in the trust-anchor set, and (if claimed) to an onDuty entry valid at time t", and receives GID encrypted only to the target domain's ACSC/KSSC (which need it for Lewko-Waters keys). Lewko-Waters is untouched; authority-side cross-authority unlinkability (Chase-Chow-style anonymous key issuing) is explicitly NOT claimed (prior art).

**C3 - ZK-COMPLY: per-entry proof of policy compliance.** pi additionally proves the hidden request satisfied the public domain policy (Rule 1 "treating doctor", Rule 2 "isDoctorAtHospital AND onDuty AND patient in emergency set"), so global verifiability of "the policy was followed" survives sealing. Treat as a stretch module, not a headline.

## 4. PoC feasibility (3 laptops)
- **Stack:** reuse HMBC2020's own stack (Solidity on Hardhat/Ganache, two separate local chains = PBC + one or two DBCs; Python middleware as the Inter-BC API) - lighter than Fabric/K8s. Crypto: Python `py_ecc` or Charm (already used by HMBC2020 for Lewko-Waters) for ElGamal/Pedersen on BN254; threshold ElGamal with Pedersen DKG (or dealer setup at stakeholder join), Chaum-Pedersen share proofs (verifiable on-chain via BN254 precompiles 0x06/0x07). ZK (C2/C3): Circom + snarkjs Groth16 (Poseidon Merkle membership depth 16-20, non-membership in sorted CRL tree, time-range check) with a public Powers-of-Tau file; on-chain Groth16 verifier from snarkjs.
- **Effort:** ~9-11 person-weeks: definitions/games 2, contracts + middleware 2.5, circuits 2, threshold opening + reconciliation 1.5, ProVerif model 1, benchmarks/writing 2.
- **Pitfalls:** Charm install on modern Python/OpenSSL; circuit constraint blow-up if certificates are ECDSA-verified inside the circuit (avoid: issue a Poseidon-hash-friendly credential/commitment at registration, verify the X.509 cert once off-circuit at RSC); gas (Groth16 verify ~200-250k gas; ZK-EHR reports 216,631); timing side channels (entry time + target domain still leak - batch per epoch); keep RAM < 3.5 GB (two Hardhat nodes + snarkjs proving for ~10k constraints is fine; no Docker needed).

## 5. Evaluation plan
- **Security (game-based):** (G1) LOG-IND: adversary controls all PBC nodes outside domain D plus < t openers, submits two honest requests (same D, epoch, outcome) and cannot tell which user/record is logged -> DDH (ElGamal), hiding commitments, ZK of pi. (G2) Opening soundness / non-frameability: an accepted entry opens (with >= t honest shares) to the real requester; no adversary makes an entry that opens to an honest user -> binding + NIZK soundness + EUF-CMA of credentials. (G3) Cross-chain completeness: a KSSC decryption without matching PBC tau is detected unless the DBC honest-majority assumption fails -> collision resistance + Merkle binding. (G4) Opening accountability: no opening without t on-chain shares.
- **Formal tool:** ProVerif model of user->PSC->DBC with `choice[]` observational equivalence for unlinkability of two users toward PBC observers, plus correspondence assertions for request authenticity (fits instructors' ProVerif + ROR taste).
- **Metrics:** per-request added latency (prove/verify), gas per log entry vs plaintext LSC baseline, proof/entry size, threshold-opening time vs n = 5..50 stakeholders, reconciliation cost per epoch vs requests/epoch, storage per 10^5 requests. **Baselines:** reimplemented plaintext HMBC2020 LSC; Fabric Idemix-style anonymity without opening; ring-signature tracing (PCTRS-style, ring size k); ZK-EHR's reported numbers.
